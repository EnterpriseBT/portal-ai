# Upgrade uuid 9→14 (packages/core) — Condensed design (#549)

**Issue:** [EnterpriseBT/portal-ai#549](https://github.com/EnterpriseBT/portal-ai/issues/549) · Task · **small / condensed** (discovery + spec + plan + smoke in one doc).

**Why.** `npm audit` (via the #545 workflow) reports a **moderate** advisory against `uuid` (`<11.1.1`, buffer-bounds in v3/v5/v6 when `buf` is provided). `packages/core` pins `uuid@^9.0.1`; the fix is a major bump to `uuid@^14.0.2`. Direct usage is a single file and uses the named `v4` export that has been stable since v7, so this is a **version bump with no code change**. Touches `packages/core` only.

## Current shape

| Piece | Location | Note |
|---|---|---|
| Only uuid import | `packages/core/src/utils/id-factory.ts:1,29` | `import { v4 } from "uuid"` → `v4()` in `UUIDv4Factory.generate()` |
| Declared range | `packages/core/package.json:139` | `"uuid": "^9.0.1"` |
| Non-imports (ignore) | `glossary.util.ts`, `portal-sql.contract.test.ts` | the word "uuid" in content/type strings, not the module |
| uuid@14 export | registry | `.` main entry still provides the `v4` named export — no API change for `v4` |
| Top-level `node_modules/uuid@9` | held by `@storybook/addon-actions@8.6.18` (#553), **not** core | core gets its own nested `14.0.2`; the shared advisory persists until storybook/dockerode/exceljs also move |

## Decision — bump the range, no code change

`uuid@^9.0.1` → `^14.0.2`. The v7→v14 breaking changes are about **dropped default export / ESM packaging / removed deep-path imports** (`uuid/v4`); `id-factory.ts` already uses the named `{ v4 }` form, so nothing in it changes. Verify by build + type-check + the core suite, not by editing code. **Scope = core's direct dep only** — the top-level `node_modules/uuid@9` is pinned by `@storybook/addon-actions` and the transitive copies under `dockerode`/`exceljs` are owned by #552/#553; this change moves core off the vulnerable `uuid` but does not (and can't) clear the shared advisory alone.

## Plan — 1 slice

**Files**
- `packages/core/package.json` — `"uuid": "^9.0.1"` → `"^14.0.2"`.
- `package-lock.json` — regenerated by `npm install`.
- `packages/core/src/utils/id-factory.ts` — **no change expected**; only touch it if type-check flags the import (it won't).

**Tests** — no new tests; a dep bump validated by existing suites. Run: `npm run build`, `npm run type-check`, `npm run lint`, and core's `npm run --workspace @portalai/core test:unit` (covers `id-factory` + everything that mints ids). Green is the gate.

## Smoke (manual, against your dev stack)

1. `npm run build && npm run type-check && npm run lint` → green; core unit suite green.
2. `npm audit` → the **aggregate `uuid` advisory persists** (still held by `@storybook/addon-actions` top-level + `dockerode`/`exceljs` transitives — #552/#553); the audit total does **not** drop from this change. The deliverable is that **core no longer contributes** to it.
3. `npm ls uuid` → core resolves `uuid@14.0.2` (`node -e "require('packages/core/node_modules/uuid/package.json').version"` → `14.0.2`). Top-level `node_modules/uuid` stays `9.0.1` (storybook), which is expected and owned elsewhere.
4. Sanity: in the app (or a node REPL against built core), a newly created entity/id still gets a well-formed UUIDv4 — ids render normally in a portal/station view.

## Out of scope

- The transitive `uuid` copies under `dockerode`/`exceljs` (clear via #552 testcontainers / #553 exceljs).
- Every other #545 finding (astro #547, maplibre #548, csv-parse #550).
