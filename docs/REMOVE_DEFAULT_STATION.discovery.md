# Remove the org-wide default station — Discovery

**Issue:** [EnterpriseBT/portal-ai#1114](https://github.com/EnterpriseBT/portal-ai/issues/1114)

**Why this exists.** The org-wide default station dates from a version with no RBAC and no seats. It assumes one station everyone starts from, but now members see different stations, and favorites (#1072, merged) give each user their own way to keep stations close. An org-chosen default no longer means anything:
- a member may not be able to read it;
- the glossary still promises behavior that doesn't exist ("used when launching a portal without picking a station");
- its star icon now sits beside the favorite star.

This is the removal that deletes the concept end to end: the column, the API field and capability, provisioning's marker, every web surface, the admin CLI flag and the help content. Past Activity entries stay readable.

## The current shape

The survey found readers and writers in core, the API, web, the admin CLI and content. There are **none** in `apps/site`, `packages/e2e`, durable `docs/`, the agent prompt or tools, `station_context`, or telemetry. **`POST /api/portals` has no server-side fallback**: `CreatePortalBodySchema` requires `stationId` (`portal.contract.ts:109-113`).

## The design space

### Decision 1 — When the column is dropped

The API runs as several ECS tasks, and `db:upgrade` migrates **before** the new tasks replace the old ones. Drizzle selects columns by name, so an old task reading `organizations` after `DROP COLUMN` fails every org read (login, the header, Settings) until it's replaced.

- **A. Drop in this PR.** One change, but every org read fails in the window between migrate and rollout.
- **B. Expand/contract.** This PR removes every reader, writer and the Drizzle column definition. The `DROP COLUMN` (`-- destructive-ok`) lands in a follow-up PR once this release is out everywhere. The column stays, nullable and unread, for one release.
- **C. Drop in this PR, deploy with the service scaled to new tasks first.** That depends on deploy choreography no other migration needs.

| | A | B | C |
|---|---|---|---|
| Rollout errors | yes, every org read during the window | none | none, if the choreography holds |
| Ships in | 1 PR | 2 PRs (the second is a one-line migration) | 1 PR + a manual deploy step |
| Precedent | — | #1070 kept `entity_tag_assignments`'s name "so the migration stays expand-only (a rename would break tasks still running the old code)" | none |

**Decided: B** (confirmed 2026-11-24; the ticket was amended to match). It's the repo's own expand-only rule, and the follow-up is trivial.

### Decision 2 — The derived-capability mechanism

`station.default.set` is the only `DERIVED_CAPABILITIES` entry, and the mechanism exists only to serve it.

- **A.** Remove the entry and the mechanism (`isDerived`, the map, its branch in the capability builder).
- **B.** Remove the entry and keep an empty map for a future derived action.

**Lean: A.** There's no current caller (per the no-speculative-infra rule), and a future one can re-add it in a few lines. CLAUDE.md:343 changes from "an action whose route checks an unconditional class grant reads a derived capability" to a plain description that such actions read `can(...)`, with no derived example.

### Decision 3 — `PATCH /api/organization` after removal

With the field gone, the body is `{ name }`.

- **A.** `name` becomes required, the refine goes, and `.strict()` turns a `defaultStationId` key into `400 ORGANIZATION_INVALID_PAYLOAD` naming it.
- **B.** Keep `name` optional and leave an empty body as a no-op.

**Lean: A.** An empty PATCH has no meaning, and a client still sending `defaultStationId` gets a precise 400 instead of a silent drop.

### Decision 4 — New Portal dialog preselection

The ticket says the picker starts empty and preselects when opened from a station page, but no station page opens this dialog (StationDetail creates the portal directly).

- **A.** Remove the default preselection. The picker starts empty, and Create stays disabled until a station is picked. Nothing new is added for station pages, since they don't use the dialog.
- **B.** Also add an optional `stationId` prop for a future caller.

**Lean: A.** The ticket's station-page case is already met by StationDetail's direct create, and B would be a prop with no caller. Removing the render-time `setTimeout` setState also fixes that wart.

### Decision 5 — `portalai org create --json` and `db:create-org` output

They return `stationId` = the default (Administrate).

- **A.** Keep `stationId`, now returning Administrate's id explicitly (looked up by `PROVISIONED_STATIONS`' Administrate entry), and document it as "the Administrate station".
- **B.** Drop `stationId` from the output.

**Lean: A.** The ticket's acceptance criteria keep `{ organizationId, stationId }`, and scripts may read it.

## Recommendation

1. **Remove `defaultStationId` everywhere it's read or written:**
   - the core model and PATCH body (`name` required, refine removed);
   - the API router and `OrganizationUpdateService` (including `beforeWrite` and `auditDefaultStationChange`);
   - the station-delete clear and its audit;
   - provisioning's `isDefault` and org update;
   - the reset and org-delete nulling;
   - the Drizzle column definition and its type checks.

   The database column stays this release, and a follow-up PR drops it with `-- destructive-ok`.
2. **Remove the capability.** `station.default.set` goes from `CALLER_CAPABILITY_ACTIONS`, and with it the `DERIVED_CAPABILITIES` mechanism. CLAUDE.md:343 is rewritten.
3. **Keep past Activity readable.** The `org.update` audit action stays. `audit-log.model.ts`'s comment and `audit-summary.util.ts` keep rendering `defaultStationId` entries, marked as legacy, with their tests kept.
4. **Remove the web surfaces:**
   - "Set as default" and the "Default" chip on station cards;
   - the "Organization Default" row on StationDetail;
   - `DefaultStationMeta` (file, test and both uses);
   - the Stations view's org fetch and `handleSetDefault`;
   - `stations.api.ts` `setDefault`;
   - the CreatePortalDialog preselection and fallback (the picker starts empty);
   - `organizations.root` from `stationDeleteKeys` unless something else needs it, with CLAUDE.md:328 to match;
   - the glossary route entry.
5. **Admin CLI.** `--default-station-id` goes from `bin.ts`, `commands/org.ts`, `store.ts` and `tables.ts`; passing it is a usage error (exit 2). `org create --json` keeps `stationId` as Administrate's id. Update `COMMANDS.md` and `README.md`.
6. **Content.** Remove the glossary term "Default Station" and its three `relatedTerms` references. Reword FAQ 85 and 374 to name Administrate without "default", drop it from the FAQ 291 Activity list, and remove FAQ 79's related term.
7. **Regenerate** `apps/api/swagger.json` and update the route-map `by:` text.

## Open questions

1. **Does anything still need `organizations.root` after a station delete?** It was there for the default. The org payload carries nothing else a station delete changes. Lean: drop it from `stationDeleteKeys`, and update CLAUDE.md:328 and the invalidation test.
2. **Does StationDetail still need the org read** (`StationDetail.view.tsx:93`) once the default row goes? Lean: remove it if the survey's "may have no other use" holds when the spec pins the file. Otherwise keep it.

## Enterprise-scale considerations

- **Concurrency & correctness.** The only concurrency in play is the rollout window. Lean: expand/contract (Decision 1), so old and new tasks both work against the same schema. Station delete stops writing the org row, so it no longer locks the org.
- **Accuracy & auditability.** Past `org.update` entries for default changes stay readable. No new ones are written, and member, role and rename audits are unchanged.
- **Failure modes.** N/A because nothing new can fail. The removed paths had their own failures (a 404 on an unreadable default), which disappear.
- **Scale & unbounded growth.** N/A, because removal only.
- **Multi-tenancy.** It removes an org-wide pointer that could name a station a member can't read, which leaked its name through the `DefaultStationMeta` link. Lean: nothing org-wide replaces it; favorites are per user.
- **Contract stability.** The org GET response loses `defaultStationId` and one capability key. The PATCH body narrows to `name`. Lean: acceptable, since the only clients are this web app and `portalai`, both updated here, and the strict 400 tells any stale client exactly what changed.
- **Data lifecycle.** The column's data is abandoned for one release, then dropped. Lean: no backfill or export, since it's a pointer with no user content.

## What this doesn't decide

- **Dashboard content** in the panel's place. That belongs to the Dashboard redesign epic.
- **Smart New Portal preselection** (last used, a favorite). It belongs to the launcher work if wanted.
- **Changing Administrate or Playground** beyond no longer marking one as default.
- **The column drop migration itself.** That's a separate one-line follow-up PR once this release is deployed (Decision 1).
